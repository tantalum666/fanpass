# Commercial Vibe Coding Playbook

## 1. 这套方法解决什么问题

Vibe Coding 最擅长把模糊意图快速变成看得见的产品，但商业项目后期容易变慢或卡住，通常不是因为页面没写出来，而是因为以下断层：

- 演示状态被当成真实状态；
- 功能列表没有产品边界和优先级；
- AI 只修复眼前症状，没有定位状态归属和根因；
- 支付、权限、并发、隐私、恢复和运维在最后才被发现；
- 代码可以运行，却没有部署、设备或用户路径证据；
- 每次对话重新解释项目，决策不断漂移；
- 免费服务适合开发，却被误当成可承诺给真实用户的基础设施；
- 为了“看起来完整”积累大量重复页面、Mock 和无法维护的胶水代码。

本 Playbook 把开发过程组织成有退出条件的阶段。阶段可以很快，但不能假装已经跨过。

## 2. 五条商业底线

1. **真实状态必须有唯一权威。** 订单、支付、库存、权限、积分、票码、风控等不能由界面或缓存自行宣布成功。
2. **完成必须有证据。** 源码存在、测试通过、已部署、真实用户路径可用，是四种不同的完成度。
3. **安全和合规是产品需求。** 它们影响登录体验、内容来源、支付流程、客服、数据结构和运营权限，不是发布前的一次扫描。
4. **原型捷径必须登记和隔离。** Mock、万能管理员、公开重置、硬编码密钥、本地成功状态可以服务原型，但不能悄悄进入真实用户路径。
5. **可维护性是速度的复利。** 清晰模块、类型、契约、测试和 Handoff 会让下一轮更快；无边界的大文件只是在向未来借时间。

## 3. 角色分工

一个人和 AI 也需要明确角色：

| 角色 | 最终责任 |
| --- | --- |
| 产品 Owner | 用户问题、商业目标、优先级、风险接受、发布批准 |
| AI/工程实现者 | 现状检查、方案、可维护实现、测试、文档和证据 |
| 设计责任 | 信息架构、状态、可访问性、品牌一致性和真实内容表现 |
| 安全/隐私责任 | 身份、权限、数据分类、威胁和发布阻塞项 |
| 运维责任 | 环境、监控、备份、恢复、成本和事故响应 |
| 外部供应商 | 只负责其明确边界；不能替产品承担业务正确性 |

早期可以一人兼任多个角色，但每个决定仍要从这些角度过一遍。

## 4. 从想法到商业产品的阶段门

### Stage 0 - Opportunity：确认值得解决的问题

目标：把“我想做一个 App”变成可验证的问题假设。

必须回答：

- 谁在什么场景遇到什么问题？
- 现有替代方案是什么，为什么不够？
- 用户为什么现在会改变行为？
- 谁付钱，为什么付钱？
- 哪些行业规则、内容权利、支付或地域要求可能让想法不可行？

退出条件：能用一页项目启动契约说清用户、价值、非目标、最大风险和第一个验证方法。没有退出前，不选完整技术栈。

### Stage 1 - Product Contract：定义产品真相

目标：建立一个不会随页面灵感漂移的产品契约。

产物：

- 核心用户旅程；
- 产品面和角色边界；
- 关键领域状态及允许的状态迁移；
- 数据/操作权限矩阵；
- 内容来源与商业使用规则；
- 版本真相：当前可发布版本、实验版本、废弃版本；
- 明确非目标。

退出条件：团队能回答“谁可以对什么做什么”“成功由谁确认”“失败时用户看到什么”。

### Stage 2 - Architecture Boundary：先定权威，再定框架

目标：确定系统边界，而不是追求一张复杂架构图。

至少标记：

- 身份与会话权威；
- 业务数据库权威；
- 支付商权威与本地映射；
- 队列、缓存、实时消息能做什么、不能做什么；
- 第三方服务不可用时的产品行为；
- 客户端、本地缓存和离线状态的边界；
- 日志中绝不能出现的字段。

退出条件：任何关键业务状态都有唯一最终裁决者，跨服务副作用有幂等和恢复策略。

### Stage 3 - Vertical Slice：做通一条真实链路

目标：完成一个小而真实的端到端路径，而不是同时铺开所有页面。

例如票务产品的第一条真实链路可以是：

`发现活动 -> 登录 -> 创建订单 -> 支付测试结果 -> 获得票 -> 展示动态票码 -> 核销一次 -> 拒绝重复核销`

要求：

- 使用真实 API 和持久化；
- 明确加载、空、失败、重试和恢复状态；
- UI 不把待处理状态显示为成功；
- 关键边界有自动测试；
- 有一条可重复的本地启动和验证命令。

退出条件：新环境中按 Runbook 能重复完成，且失败路径不会破坏业务不变量。

### Stage 4 - Honest Alpha：从“能演示”到“状态可信”

目标：清除演示幻觉，让功能面对现实数据。

工作重点：

- 把 Mock 仅留在 Preview/Fixture；
- 所有 active path 读取真实后端；
- 删除本地假成功和吞错；
- 为并发、重试、重复 Webhook、重复点击和进程重启设计；
- 拆分角色产品面；
- 对错误、空数据和不可用状态做诚实 UI；
- 记录仍保留的原型捷径。

退出条件：演示不需要手改数据库；关掉一个依赖时产品会明确降级，而不是假装成功。

### Stage 5 - Secure Beta Foundation：真实用户前的发布底座

目标：关闭会直接伤害用户、资金或数据的风险。

最低门槛：

- 生产式身份验证和服务端授权；
- 精确 Origin/CORS/Cookie/CSRF 边界；
- 响应隐私分类和日志脱敏；
- 密钥仅在受控环境，具备轮换方式；
- 支付签名验证、幂等、补偿和对账；
- 数据库迁移、备份、恢复演练；
- 依赖审计按运行时边界判断，不盲目 `--force`；
- 关键操作审计日志；
- Staging 与生产数据、密钥和权限分离；
- 法律文本、内容授权、客服和删除/导出路径有 Owner。

退出条件：关键和高风险要么修复，要么由 Owner 书面接受；“扫描为零”不能代替真实威胁边界。

### Stage 6 - Closed Beta：让少量真实用户暴露系统问题

目标：在可控人群中验证产品、可靠性和运营。

要求：

- 非休眠计算承载外部依赖路径；
- uptime、错误率、p95、数据库连接、异步积压和费用告警；
- 可撤销的邀请和权限；
- 支持渠道和事故记录；
- 设备/浏览器真实路径测试；
- 灰度发布和回滚；
- 用户反馈要关联任务、证据和产品决定。

退出条件：非技术用户能完成核心旅程；团队可以定位失败、恢复服务并解释数据状态。

### Stage 7 - Paid Pilot：证明钱和责任都能闭环

目标：小范围承担真实交易责任。

额外门槛：

- 支付、退款、争议、发票/税务和客服流程；
- 库存/权益并发负载测试；
- RPO/RTO 和恢复演练；
- 供应商 SLA、预算和超额保护；
- 服务条款、隐私政策、内容版权和地区合规；
- 运营 Console 不依赖工程师手工改库；
- 每个关键变更都有审计和授权。

退出条件：一次真实交易从购买到售后可完整对账，一次故障可以在承诺时间内恢复。

### Stage 8 - Scale：用指标触发扩展，不用想象

目标：在不牺牲业务正确性的前提下提高容量和地域覆盖。

扩展顺序：

1. 观测和定位；
2. 修查询、缓存和热点；
3. 垂直扩容；
4. 拆出 Worker 和共享协调；
5. 水平扩容；
6. 边缘缓存和流量准入；
7. 有持续需求时增加区域事务平面；
8. 只有 TCO、合规或 SLA 证明合理时迁移大云。

退出条件不是“完成扩展”，而是每次容量决策都有测量、预算、回滚和下一触发点。

## 5. 一次工作会话的标准循环

### 5.1 Orient - 先恢复真相

- 读 Handoff、当前任务和相关契约；
- 检查 Git 状态，保护用户未完成修改；
- 检查当前可运行版本、部署 SHA 和环境；
- 不从旧截图或旧聊天推断现状。

### 5.2 Frame - 把需求改写成结果

任务不是“优化 Explore”，而是：

> 让用户在不知道活动名称时，也能在 30 秒内通过兴趣、艺人、地点或内容线索找到值得关注的活动，并且在无内容、网络失败和未登录时仍知道下一步。

同时写清非目标、数据权威、安全/隐私、内容权利和验收证据。

### 5.3 Inspect - 先找根因

- 运行现有路径；
- 从 UI、客户端状态、网络、BFF/API、数据库、供应商、部署逐层检查；
- 保存错误类别和状态码，不保存敏感值；
- 找到最小可证伪假设。

### 5.4 Design - 先定边界和失败状态

- 选择最小可维护改动；
- 复用现有模块；
- 明确状态机和不变量；
- 先设计空、错、等待、过期和重试，再设计 happy path；
- 有重大取舍时写 Decision Record。

### 5.5 Build - 做垂直切片

- 先契约/类型，再领域逻辑，再适配器，再 UI；
- 第三方 SDK 隔离在边界层；
- 不在视图里复制业务规则；
- 不顺手重构与任务无关的用户修改。

### 5.6 Verify - 四层证据

| 层次 | 问题 | 常见证据 |
| --- | --- | --- |
| 静态 | 代码结构和类型是否正确？ | typecheck、lint、contract audit |
| 自动 | 关键行为和回归是否被保护？ | unit/integration/concurrency tests |
| 运行 | 真实环境是否执行了新代码？ | deploy SHA、health、log、API smoke |
| 体验 | 用户是否真的能完成？ | simulator/device/browser E2E、视觉检查 |

高风险功能还要加恢复、并发、安全和隐私证据。

### 5.7 Close - 交付与沉淀

- 说明结果、验证和剩余风险；
- 更新 Handoff 当前状态；
- 更新相关契约和任务；
- 本次进展写入 Journey；阶段变化时补充归纳总结；
- 不自动购买服务、迁移生产或扩大权限，除非 Owner 明确授权。

## 6. Bug 排查协议

当用户说“点了没反应”“一直跳转”“挂久了刷新不了”时，按以下层次排查：

1. **交互层**：按钮是否可点、事件是否触发、导航是否被覆盖；
2. **客户端层**：状态机、缓存、401、过期 Token、重试是否正确；
3. **网络层**：URL、DNS、TLS、CORS、Cookie、Origin、超时；
4. **应用层**：BFF/API 路由、角色、限流、错误映射；
5. **数据层**：迁移、事务、锁、连接和真实记录；
6. **供应商层**：Privy/Stripe/邮件/RPC 配置和限额；
7. **部署层**：服务是否休眠、部署是否是目标 SHA、环境变量是否生效。

每次只推进一个可验证假设。修复后增加永久回归测试，并用用户真实路径重跑。FanPass 的 Console 登录说明：冷启动、身份登录成功、跨域会话同步、后端角色授权是四个不同问题。

## 7. 产品设计协议

### 7.1 从任务而不是页面出发

先写用户任务、决策和焦虑，再画导航和卡片。一个页面信息很多时，优先建立搜索、筛选、分组和子页面层级，而不是无限横向滚动。

### 7.2 所有页面必须覆盖六种状态

- 首次加载；
- 有数据；
- 空数据；
- 网络或服务失败；
- 未登录/无权限；
- 数据过期但仍有可用缓存。

### 7.3 内容产品必须把版权做成数据

活动、艺人、潮流资讯等内容，每条记录至少需要：来源、作者/权利方、原始 URL、授权类型、允许用途、地域、到期时间、图片权利、编辑状态和下架记录。不要把“网上能看到”理解为“可以商用转载”。

### 7.4 Web3 必须隐藏复杂度

- 钱包是身份/证明来源，不是强迫用户学习的入口；
- 链上证明不替代数据库交易权威；
- 积分和任务应解释价值、进度和分配方式；
- 反作弊阈值保留在后端，不向用户公开可被利用的上限；
- 允许正常用户合理的设备/钱包变化，但对批量模式渐进加摩擦；
- 不用繁琐任务、焦虑倒计时或不透明概率 PUA 用户。

## 8. 代码与架构协议

- 一个模块只拥有一类变化原因；
- 业务规则进入领域/服务层，UI 只表达状态和意图；
- 供应商 SDK 放在适配器边界，核心领域使用自有类型；
- 状态迁移、金额、权限和库存使用强类型/枚举，不靠散落字符串；
- 跨系统副作用使用事务 Outbox、幂等键、重试和补偿；
- 缓存、队列和边缘层提高性能，不拥有库存、资金或权益；
- 水平扩容前先处理进程内限流、调度器和实时广播；
- 数据库 schema 变更使用可审核迁移，不在生产构建时直接 push；
- 大文件在有生命周期测试保护后按领域拆分，不为“整洁”盲拆；
- 对用户未授权的外部写入、付费升级和生产迁移必须停下来确认。

## 9. 依赖与第三方服务协议

选供应商时记录：功能、运行时边界、价格触发器、数据流向、退出方案和失败体验。

依赖审计按四类处理：

1. 生产运行时；
2. 隔离运行时；
3. 构建/开发工具；
4. 不可达或已移除代码。

生产运行时漏洞优先修复。工具链问题也要跟踪，但不要为了数字归零使用破坏性升级。升级后必须重新跑类型、构建、测试、运行路径和安全边界。

## 10. 基础设施与成本协议

每个阶段记录：用户量、峰值、SLO、RPO/RTO、月预算、账单告警和升级触发器。

原则：

- Free 只服务内部原型和可接受冷启动的预览；
- 外部用户依赖前移到非休眠容量；
- API 与数据库靠近；公共内容尽量边缘化；
- 全球用户不等于第一天做全球多主数据库；
- 有交易权威的对象一次只在一个区域写；
- 迁移 AWS/GCP 需要功能、合规、SLA 或三年 TCO 证据；
- 没有基础设施 Owner 和 On-call 时，不因为“看起来专业”上 Kubernetes。

## 11. 商业发布评分卡

每项按 `0 = 未定义`、`1 = 有方案/局部实现`、`2 = 已验证` 评分：

| 维度 | 关键问题 |
| --- | --- |
| 用户价值 | 目标用户能否独立完成核心任务？ |
| 状态正确性 | 所有关键状态是否有唯一权威和不变量？ |
| UX 完整性 | 加载、空、错、权限、过期和恢复是否完整？ |
| 可维护性 | 模块、类型、测试和文档能否支持继续迭代？ |
| 安全隐私 | 身份、权限、密钥、响应和日志是否有证据？ |
| 交易可靠性 | 幂等、并发、补偿、对账和恢复是否验证？ |
| 内容合规 | 来源、许可、下架和用户数据权利是否明确？ |
| 发布运维 | 部署、监控、回滚、备份和支持是否可执行？ |
| 成本可控 | 当前账单和下一升级触发器是否清楚？ |
| 证据完整 | 代码、自动、运行、体验证据是否匹配同一版本？ |

内部原型不要求满分。Closed Beta 前不应有任何 0；真实付费 Pilot 前，涉及资金、权限、隐私、库存和恢复的维度必须为 2。

## 12. 最常见的伪进度

- 页面齐全，但按钮只改本地状态；
- 测试通过，但测试的是 Mock，不是生产路径；
- 服务 200，但实际部署不是刚改的提交；
- 登录成功，但后端没有创建被授权的业务会话；
- `npm audit` 为零，却没有权限、隐私或密钥边界；
- 有 K 线图，却来自虚构交易；
- 全球可访问，却让所有交易跨洲访问同一个远端数据库；
- 有 Web3，却把助记词、Gas、网络切换和任务农场压力交给普通用户；
- 上了 Redis/队列，却仍让缓存决定库存；
- 文档很多，但当前版本、Owner 和下一步仍不清楚。

识别伪进度的简单问题是：

> 如果现在关掉开发者电脑、刷新真实设备、重复提交两次、让依赖超时，并让另一个用户同时操作，产品还知道真实状态吗？

## 13. 在下一个项目中如何更快

不要复制 FanPass 的全部工程量。复制它已经验证过的顺序：

1. 一页机会契约；
2. 一条真实垂直链路；
3. 领域状态与权威；
4. 原型捷径登记；
5. 四层证据；
6. 阶段门发布；
7. 持续进展与阶段校准进入 Journey；
8. 只有跨项目成立的经验进入 Playbook。

真正的顺畅不是一次不出错，而是每次错误都能更快分层、被永久保护，并让下一次不用从零开始。
