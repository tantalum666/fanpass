# Provider Cost And Feature Feasibility

Date: 2026-05-28

This document tracks whether FanPass can build Alpha/Beta flows on low-cost or free-tier provider plans. Re-check this before any real-user Beta because Stripe and Privy pricing/features can change.

## Stripe

Current assessment: suitable for low-cost Alpha/Beta testing.

Official references:

- [Stripe pricing](https://stripe.com/pricing)
- [Stripe webhooks](https://docs.stripe.com/webhooks)
- [Stripe testing use cases](https://docs.stripe.com/test-mode)
- [Stripe webhook endpoints API](https://docs.stripe.com/api/webhook_endpoints)

Relevant findings:

- Stripe standard pricing is transaction-based. Stripe says there are no setup fees or monthly fees on standard pricing, while payment fees depend on the payment method.
- Stripe Checkout/Payments are listed as included with Payments on standard pricing.
- Stripe docs support test environments/sandboxes for testing without moving real money.
- Stripe docs support webhook endpoints for account events, local CLI testing, and signature verification.
- Basic HTTPS webhook endpoints are normal Stripe integration infrastructure. Advanced event destination patterns such as Amazon EventBridge are not required for FanPass Beta.

FanPass decision:

- Keep the current PaymentIntent + webhook architecture.
- Use Stripe test mode for Beta validation.
- Do not require paid Stripe add-ons for Alpha/Beta unless later product scope requires Connect, Tax, Billing, custom domains, advanced reporting, or instant payouts.
- Payment-aware order settlement is now guarded behind `FANPASS_REQUIRE_PAYMENT_AUTHORIZATION`. When enabled, Prisma settlement only matches buy orders that have an authorized or captured payment record, and Stripe/mock webhook authorization enqueues an idempotent order-match retry side-effect.
- Backend payment side-effect handlers now cover PaymentIntent capture, authorization cancellation, refund, and reconciliation. Local/mock verification covers authorization -> match -> ownership transfer -> capture, and 2026-06-03 Render staging evidence validates Stripe test-key capture, cancellation, refund, reconciliation, replay/idempotency, and healthy residual outbox state.
- Payment capture, authorization cancellation, and refund workers now pass the durable outbox job idempotency key into the Stripe provider boundary, so provider retries line up with the persisted side-effect job instead of using an unrelated ad hoc key.

- Stripe webhook event ids are now persisted in `payment_webhook_events`; duplicate replay of the same event id is acknowledged without repeating payment state updates, audit writes, or outbox jobs.
- Admin-only payment operation triggers now create idempotent outbox jobs for authorization cancellation, refund, and reconciliation. These are backend/admin controls only; 2026-06-03 Render staging evidence validated real Stripe test-mode execution before any real-money use.
- `npm run security:payment-response-redaction` locks the local payment response boundary so only authenticated payer checkout intent responses may expose a client secret; admin payment operations, webhook responses, side-effect payloads, and operations snapshots remain redacted before Stripe test-mode evidence is trusted.

## Privy

Current assessment: suitable for core low-cost auth/wallet testing. Privy production webhooks are not part of the current low-cost Beta foundation path because official Privy docs say production webhooks require upgrading to Enterprise and the pricing page lists Webhooks with Enterprise controls.

Official references:

- [Privy pricing](https://www.privy.io/pricing)
- [Privy authentication docs](https://docs.privy.io/authentication/user-authentication/privy-auth)
- [Privy access token docs](https://docs.privy.io/authentication/user-authentication/tokens)
- [Privy webhooks docs](https://docs.privy.io/user-management/users/webhooks/handling-events)
- [Privy wallet overview](https://docs.privy.io/wallets/overview)

Relevant findings:

- Privy Developer pricing starts with a free 0-499 MAU tier. The pricing page says Developer plans include core features, including embedded wallets, unified login, SDK/UI, analytics, and monthly free signature/transaction volume.
- Privy docs support email/SMS, passkeys, OAuth/social login, wallet login, access tokens, backend token verification, and embedded wallets.
- Privy docs describe signed webhook payloads for user, wallet, and MFA events, and the webhook overview says production webhooks require upgrading to Enterprise.
- Pricing interpretation: the pricing page also highlights Webhooks with Enterprise features. FanPass therefore does not assume Privy webhooks are available on Developer/low-cost plans without dashboard verification or written confirmation.

- Core Privy login and embedded wallet integration is implemented for the current Beta foundation scope through FanPass/FanPass Ops Swift SDK OTP and isolated FanPass Console React SDK login.
- Do not make Privy webhooks a hard dependency for Alpha/Beta low-cost testing.
- Prefer backend access-token verification and explicit app-server synchronization on login/session refresh as the low-cost path.
- Add Privy webhooks only after verifying the selected plan supports them.
- Do not add a webhook route or `PRIVY_*WEBHOOK*` secret requirement for the current Beta foundation path.

## Engineering Maintainability Rule

FanPass must not accumulate unstructured "just make it work" code that blocks future changes.

Required engineering constraints:

- Keep provider integrations behind narrow service boundaries, not scattered directly across controllers, SwiftUI views, or dashboard components.
- Keep domain lifecycle code separate from Stripe, Privy, chain, NFC, and QR provider code.
- Use typed contracts, DTOs, schema validation, and automated tests for payment, auth, ticket lifecycle, and scanner flows.
- Avoid duplicating settlement, authorization, and ownership logic across product surfaces.
- Every new external side effect must be idempotent, auditable, retry-aware, and isolated enough to swap provider implementations later.
- If a quick prototype shortcut is used, document it immediately with an owner, risk, and replacement path before it becomes product foundation.
