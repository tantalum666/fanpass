# FanPass QA Checklist

Use this checklist before calling a version or milestone complete.

## Start-of-Work Checklist

- Read `docs/CODEX_HANDOFF.md` first.
- Enumerate and read every Markdown file in the workspace with `rg --files -g '*.md'` before changing code, evidence, or product docs.
- Treat `docs/NEW_CHAT_PROMPT.md` as the generated resume prompt to update at the end of work, not as the first source to read at startup.
- Read Clean V4 sources before changing UI, marketing copy, colors, typography, iconography, or layout: `FanPass_VI_Redesign_V4/`, `docs/brand/FanPass_VI_Clean_V4_Audit.md`, `docs/brand/FanPass_UI_Guardrails.md`, and `docs/brand/FanPass_Final_Design_Tokens_V4.md`.
- Read `docs/BETA_ROADMAP.md`.
- Read `docs/DEVELOPMENT_TASKS.md`.
- Confirm whether the current change belongs to `FanPass`, `FanPass Ops`, `FanPass Console`, API, contracts, or shared packages.
- Update docs immediately when product boundaries change.
- Update docs in the same change when evidence status, provider assumptions, release blockers, standing user instructions, or external-testing claims change.
- Before ending the work session, update the relevant Markdown docs with what changed, what passed, and known gaps.
- Before ending the work session, update `docs/NEW_CHAT_PROMPT.md` when durable state, blockers, or standing instructions changed.
- Before resuming Web Beta Fallback implementation after 2026-06-15, confirm the owner has provided the extra requirements, then repeat the Markdown startup pass and re-read the Web source docs.
- When hardware bench work changes, update `docs/OPS_SCANNER_DEVICE_EVIDENCE.md`, `docs/technical/FanPass_QR_NFC_Verification_Plan_V4.md`, `docs/NFC_NDEF_TAG_FIXTURE.md`, and `docs/DEVELOPMENT_TASKS.md` as applicable.

## Product Boundary Checks

- Fan app must not show gate scanner controls in the default C-side navigation.
- Gate scanner belongs in `FanPass Ops`.
- Fan app must not register or expose a staff scanner deep link in normal prototype builds.
- Fan app must not declare Camera/NFC permissions unless a consumer feature truly requires them.
- FanPass Ops login must not expose local demo/test staff shortcuts or user-facing test staff copy in beta-facing builds.
- Organizer controls belong in `FanPass Console`, not in either fan wallet or gate scanner flows.
- Fan app must open to a browsable home screen for signed-out users.
- Auth should appear at action time, not as a launch-time wall.
- Auth/session must exist before private wallet, order placement, task submission, or profile management flows are considered complete.
- Web3 terms should be hidden behind plain user-facing language unless the screen is explicitly technical.
- `FanPass Ops` may use operational terms such as gate, scan, redeem, rejected, duplicate, and offline.
- `FanPass Console` may use admin terms such as inventory, audit log, settlement, risk, and review.

## Brand Checks

- UI changes must use Clean V4 tokens from `docs/brand/FanPass_Final_Design_Tokens_V4.md` and `docs/brand/fanpass-brand-tokens.json`.
- Logo usage must use only Ink Pass, Signal Blue, Verify Mint, and White.
- Semantic colors such as Amber Cap and Coral Risk must not be treated as brand/logo colors.
- New consumer screens should feel fan-first and venue-grade, not crypto-first or exchange-first.
- FanPass Ops screens should feel operational, fast, and high-clarity rather than consumer-marketing oriented.
- FanPass Console screens should be dense, quiet, and optimized for repeated administrative work.
- Cards use 8 px radius unless a platform control requires otherwise.
- Do not add decorative blobs, bokeh, generic gradients, or crypto visual cliches.
- Keep the Figma VI board and local token files in sync when brand decisions change.
- Do not use iOS prototype screenshots as VI artifacts; screenshots are engineering QA only.
