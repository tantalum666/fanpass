# FanPass QR NFC Verification Plan V4

Status: local backend/iOS foundation implemented; physical-device and production hardening remain open
Date: 2026-06-05

## Current Implementation Snapshot

Local implementation now includes:

- Backend QR payload generation through `VerificationService.createPayload`.
- Versioned signed entry payload fields: `v`, `credentialId`, `ticketId`, `eventId`, `ticketTypeId`, `ownerIdHash`, `nonce`, `issuedAt`, `expiresAt`, `entryMode`, `kid`, and `signature`.
- HMAC-SHA256 signature over canonical sorted JSON with base64url output.
- Backward-compatible verification for older hex signatures.
- Production-like fail-fast when `QR_SIGNING_SECRET` is missing or unsafe.
- Optional `QR_SIGNING_KEY_ID` support through the `kid` field.
- Staff-only QR redemption through `/verification/redeem`.
- Staff-only NFC validation/redemption through `/verification/nfc/validate`.
- FanPass Ops NFC reader path that sends captured NDEF payloads to the NFC validation endpoint.
- API route-role regression tests and verification service tests for signed QR, duplicate rejection, NFC URI payload redemption, wrong-event NFC rejection, gate assignment, listed-ticket blocking, and production secret enforcement.
- QR credentials are limited to a 30-second backend TTL. Fan iOS and web Ticket Detail refresh the displayed credential before expiry; backend admission state remains authoritative if a client fails to refresh.

Still open:

- Redis nonce lock for distributed replay prevention.
- Signed physical-device NFC evidence.
- Real HTTPS staging/beta API evidence with signed iOS/FanPass Ops builds.
- Secret-manager backed signing key rotation.

## Dynamic QR Credential Design

QR credentials are short-lived, signed, owner-only entry credentials. They are generated by backend for active tickets and redeemed by staff scanner through the check-in API.

## QR Payload Fields

Suggested payload:

```json
{
  "v": 1,
  "credentialId": "uuid",
  "ticketId": "uuid-or-safe-fragment",
  "eventId": "uuid",
  "ticketTypeId": "uuid",
  "ownerIdHash": "hmac-owner-fragment",
  "nonce": "random-128-bit",
  "issuedAt": "iso8601",
  "expiresAt": "iso8601",
  "entryMode": "qr",
  "kid": "signing-key-id",
  "signature": "base64url"
}
```

Do not include personal data, payment IDs, full wallet addresses, or provider secrets.

## Signature Strategy

- Backend signs canonical payload using server-held signing key.
- Scanner/backend verifies signature.
- Key rotation requires `kid` field.
- Signing keys live in secret manager, not app bundle.
- Scanner should not need private keys.

## Expiry And Nonce

- Expiry target: 30 seconds.
- Fan-facing clients should refresh before expiry, using approximately `expiresAt - 5s` so a normally connected device presents a fresh code every 25 seconds.
- Nonce stored as hash in `qr_credentials`.
- Use atomic redemption check.
- Expired credentials return a clear refresh instruction.

## Replay Attack Prevention

- Unique nonce per credential.
- Redis set-if-not-exists for fast replay detection.
- PostgreSQL unique constraint on accepted credential/ticket redemption.
- One accepted check-in per ticket/event.
- Staff scanner rate limiting.

## Core NFC Scanner-Side Verification

Initial NFC scope:

- Staff device reads NDEF tag.
- NDEF payload maps to a ticket credential or tag reference.
- Scanner sends payload to backend validation endpoint.
- Backend maps NFC credential to ticket and check-in logic.

Do not imply consumer iPhone card emulation.

## NDEF Payload Design

Supported NFC payloads are wrappers around the same signed entry payload used by QR. FanPass Ops supports:

- NDEF Text record containing the signed entry payload JSON.
- NDEF URI record using `fanpass://entry?payload=<url-encoded-signed-entry-payload-json>`.

The backend normalizes the text or URI payload, parses the signed entry payload, confirms that the selected scanner event matches `eventId`, then reuses the same signature, expiry, nonce, ticket status, ownership, role, and gate assignment validation path as QR.

Current signed entry payload shape:

```json
{
  "v": 1,
  "credentialId": "uuid",
  "ticketId": "uuid-or-safe-fragment",
  "eventId": "uuid",
  "ticketTypeId": "uuid",
  "ownerIdHash": "hmac-owner-fragment",
  "nonce": "random-128-bit",
  "issuedAt": "iso8601",
  "expiresAt": "iso8601",
  "entryMode": "qr-or-nfc",
  "kid": "signing-key-id",
  "signature": "base64url"
}
```

Tag UID should be hashed if stored.

## NFC Wristband/Card/Tag Concept

- NFC wristband or card can carry an NDEF credential reference.
- Backend controls validity.
- Tags should be revocable.
- Lost tag handling requires support workflow.
- NFC credentials should not contain long-lived secrets.

## Check-In Validation Flow

1. Staff selects assigned event and gate.
2. Staff scans QR or NFC.
3. App parses payload shape.
4. App sends QR credential to `/verification/redeem` or NFC NDEF payload to `/verification/nfc/validate`.
5. Backend verifies role, event assignment, signature, expiry, nonce, ticket status, transfer/listing status, refund/cancel state.
6. Backend atomically records accepted/rejected result.
7. App shows accepted/rejected state with reason.

## Offline Fallback Concept

Offline scanner can:

- Validate signature and expiry if it has public verification material.
- Queue pending check-ins.
- Show `pending sync` state.

Risks:

- Duplicate redemption across multiple offline gates.
- Revoked/refunded ticket not known locally.
- Clock drift.

MVP should require online check-in unless a formal offline policy is implemented.

## Duplicate Redemption Prevention

- Database unique accepted check-in per ticket/event.
- Redis nonce lock for fast gate response.
- Idempotent check-in request ID.
- Staff UI shows already redeemed with last safe gate/time summary.
- Ops QR/NFC scans and physical turnstile scans must converge on the same backend redemption boundary. The first request that atomically updates the ticket from `ACTIVE` or `TRANSFERRED` to `REDEEMED` wins; every later or concurrent request for that ticket returns `DUPLICATE`, even if a second fan device presents a different signed QR nonce for the same ticket.
- Client, Arduino, LCD, servo, or scanner-local duplicate state is never the final source of truth. It may short-circuit obvious repeat reads for UX, but accepted entry must come from FanPass API.

## Failure States

- Valid ticket.
- Already redeemed.
- Invalid ticket.
- Wrong event.
- Expired credential.
- Cancelled/refunded ticket.
- Listed ticket reserved for resale.
- NFC tag unreadable.
- NFC credential expired.
- Network unavailable.
- Unknown verification error.

## 2026-06-24 Admission Timing Boundary Hardening

Status: API unit-verified; physical scanner evidence still open

- Redemption now rejects signed entry credentials whose `issuedAt` is more than 5 seconds in the future. This prevents a future-valid code from being accepted early if a client clock, test path, or stale signer produces an invalid window.
- Redemption now rejects signed entry credentials whose `expiresAt - issuedAt` exceeds the server TTL plus 5 seconds of clock skew. This prevents a valid signature from turning into a long-lived screenshot credential.
- For backend-issued credentials with `credentialId`, redemption now also requires the signed `issuedAt` and `expiresAt` to match the stored active credential. This prevents a validly signed payload from shifting the server-issued credential window.
- Existing behavior remains: expired credentials are rejected, superseded credentials are rejected after QR refresh, and same-ticket races produce exactly one accepted redemption.
- Verification passed:

```bash

scripts/with-node-22.sh npm run typecheck -w apps/api
```

## 2026-06-15 Arduino EP8280 Mock Turnstile Bench

Status: local hardware bench QR path working; product QR evidence still open for current TestFlight, and NFC NDEF evidence remains a future release path.

A local Arduino mock turnstile was added at `hardware/fanpass_turnstile/fanpass_turnstile.ino` to support hardware learning before continuing Web work. It uses Arduino UNO R4 WiFi, EP8280 NFC/QR scan engine, I2C LCD, HC-SR04 ultrasonic sensor, and one micro servo.

Current verified bench behavior:

- EP8280 is connected through the 8-pin interface in TTL mode.
- QR scans can now produce real TTL bytes on Arduino `Serial1`; serial output includes `SCAN: <real QR text>`. Per-byte EP8280 diagnostics remain available behind a disabled debug flag, but are off by default so long signed QR payloads do not stall scanner reads.
- `scripts/fanpass-turnstile-redemption-bridge.mjs` can be run through `npm run hardware:turnstile:bridge` to read those `SCAN: <real QR text>` serial lines from the USB-connected Arduino and submit signed FanPass QR JSON to `POST /verification/turnstile/redeem` with `FANPASS_TURNSTILE_REDEEM_KEY`, or to the existing staff route with `FANPASS_STAFF_ACCESS_TOKEN`. This is required for a scanned fan-phone QR to become `REDEEMED` in the backend and then display as used in the FanPass phone app.
- EP8280 Pin7 decode-success output is still monitored for diagnostics, but the code now delays that fallback to let TTL payloads arrive first.
- LCD status copy is configured for ready, verifying pass, valid pass, gate open, pass complete, timeout, invalid pass, and no-QR-data states.
- The servo gate opens for signed FanPass QR JSON payloads. Arbitrary scanner noise is rejected instead of being treated as a valid pass.
- The local duplicate guard keys dynamic QR scans by `credentialId` or `nonce`, not by `ticketId`, so a newly refreshed QR for the same ticket can still reach backend redemption.
- The ultrasonic sensor detects pass-through and marks the local gate flow as passed.
- Enclosure CAD/STL planning exists under `docs/hardware/FanPass_Turnstile_Enclosure_Spec.md` and `hardware/fanpass_turnstile/enclosure/`. The current preferred local print candidate is `fanpass_turnstile_front_panel_fitcheck_computeruse_v5.stl`, followed by `fanpass_turnstile_shell_computeruse_v5.stl` and `fanpass_turnstile_rear_lid_computeruse_v5.stl` only after fit-check. This is mechanical cleanup only, not product QR/NFC evidence.

Current bench limitations:

- EP8280 NFC card/tag behavior is not working yet in this setup.
- Pin7 decode-success alone does not provide QR text. It remains enabled only as temporary bench-open fallback behavior and is not FanPass ticket validation.
- The bench prototype itself is not connected to FanPass API redemption, signed dynamic entry credentials, backend nonce checks, gate assignment, scanner identity, or HTTPS staging unless the separate host bridge is running with a Render-configured turnstile key or staff/admin bearer token. The bridge defaults to Python `pyserial` mode for UNO R4 stability and expects `pyserial` to be installed in the active Python environment. Without that bridge, the Arduino can open the servo and reject a repeated local scan, but the phone will not show the ticket as used because no backend ticket state changed. The servo hold loop has a 10-second hard-close guard and the ready screen reinitializes the I2C LCD to recover from scanner/servo noise during long QR scans.
- Arduino/breadboard rail power may be unstable under scanner/servo load until a separate regulated 5V supply is added.
- No physical enclosure print or fit-test has been completed yet.

Boundary:

- This bench is not a replacement for FanPass Ops physical QR validation.
- It does not close the QR blocker, future NFC blocker, TestFlight blocker, Apple Wallet blocker, or chain custody blocker.
- Do not save raw signed FanPass QR payloads, nonces, bearer tokens, device identifiers, or real ticket/user data in Arduino logs or hardware notes.
