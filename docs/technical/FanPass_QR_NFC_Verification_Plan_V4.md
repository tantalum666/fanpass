# FanPass QR NFC Verification Plan V4

Status: local backend/iOS foundation implemented; physical-device and production hardening remain open
Date: 2026-06-05

## Current Implementation Snapshot

Local implementation now includes:

- Backend QR payload generation through `VerificationService.createPayload`.
- Versioned signed entry payload fields: `v`, `credentialId`, `ticketId`, `eventId`, `ticketTypeId`, `ownerIdHash`, `nonce`, `issuedAt`, `expiresAt`, `entryMode`, `kid`, and `signature`.
- HMAC-SHA256 signature over canonical sorted JSON with base64url output.
- Backward-compatible verification for older hex signatures.
- Production-like fail-fast when `QR_SIGNING_SECRET` is missing or unsafe.
- Optional `QR_SIGNING_KEY_ID` support through the `kid` field.
- Staff-only QR redemption through `/verification/redeem`.
- Staff-only NFC validation/redemption through `/verification/nfc/validate`.
- FanPass Ops NFC reader path that sends captured NDEF payloads to the NFC validation endpoint.
- API route-role regression tests and verification service tests for signed QR, duplicate rejection, NFC URI payload redemption, wrong-event NFC rejection, gate assignment, listed-ticket blocking, and production secret enforcement.
- QR credentials are limited to a 30-second backend TTL. Fan iOS and web Ticket Detail refresh the displayed credential before expiry; backend admission state remains authoritative if a client fails to refresh.

Still open:

- Redis nonce lock for distributed replay prevention.
- Signed physical-device NFC evidence.
- Real HTTPS staging/beta API evidence with signed iOS/FanPass Ops builds.
- Secret-manager backed signing key rotation.

## Dynamic QR Credential Design

QR credentials are short-lived, signed, owner-only entry credentials. They are generated by backend for active tickets and redeemed by staff scanner through the check-in API.

## QR Payload Fields

Suggested payload:

```json
{
  "v": 1,
  "credentialId": "uuid",
  "ticketId": "uuid-or-safe-fragment",
  "eventId": "uuid",
  "ticketTypeId": "uuid",
  "ownerIdHash": "hmac-owner-fragment",
  "nonce": "random-128-bit",
  "issuedAt": "iso8601",
  "expiresAt": "iso8601",
  "entryMode": "qr",
  "kid": "signing-key-id",
  "signature": "base64url"
}
```

Do not include personal data, payment IDs, full wallet addresses, or provider secrets.

## Signature Strategy

- Backend signs canonical payload using server-held signing key.
- Scanner/backend verifies signature.
- Key rotation requires `kid` field.
- Signing keys live in secret manager, not app bundle.
- Scanner should not need private keys.

## Expiry And Nonce

- Expiry target: 30 seconds.
- Fan-facing clients should refresh before expiry, using approximately `expiresAt - 5s` so a normally connected device presents a fresh code every 25 seconds.
- Nonce stored as hash in `qr_credentials`.
- Use atomic redemption check.
- Expired credentials return a clear refresh instruction.

## Replay Attack Prevention

- Unique nonce per credential.
- Redis set-if-not-exists for fast replay detection.
- PostgreSQL unique constraint on accepted credential/ticket redemption.
- One accepted check-in per ticket/event.
- Staff scanner rate limiting.

## Core NFC Scanner-Side Verification

Initial NFC scope:

- Staff device reads NDEF tag.
- NDEF payload maps to a ticket credential or tag reference.
- Scanner sends payload to backend validation endpoint.
- Backend maps NFC credential to ticket and check-in logic.

Do not imply consumer iPhone card emulation.

## NDEF Payload Design

Supported NFC payloads are wrappers around the same signed entry payload used by QR. FanPass Ops supports:

- NDEF Text record containing the signed entry payload JSON.
- NDEF URI record using `fanpass://entry?payload=<url-encoded-signed-entry-payload-json>`.

The backend normalizes the text or URI payload, parses the signed entry payload, confirms that the selected scanner event matches `eventId`, then reuses the same signature, expiry, nonce, ticket status, ownership, role, and gate assignment validation path as QR.

Current signed entry payload shape:

```json
{
  "v": 1,
  "credentialId": "uuid",
  "ticketId": "uuid-or-safe-fragment",
  "eventId": "uuid",
  "ticketTypeId": "uuid",
  "ownerIdHash": "hmac-owner-fragment",
  "nonce": "random-128-bit",
  "issuedAt": "iso8601",
  "expiresAt": "iso8601",
  "entryMode": "qr-or-nfc",
  "kid": "signing-key-id",
  "signature": "base64url"
}
```

Tag UID should be hashed if stored.

## NFC Wristband/Card/Tag Concept

- NFC wristband or card can carry an NDEF credential reference.
- Backend controls validity.
- Tags should be revocable.
- Lost tag handling requires support workflow.
- NFC credentials should not contain long-lived secrets.

## Check-In Validation Flow

1. Staff selects assigned event and gate.
2. Staff scans QR or NFC.
3. App parses payload shape.
4. App sends QR credential to `/verification/redeem` or NFC NDEF payload to `/verification/nfc/validate`.
5. Backend verifies role, event assignment, signature, expiry, nonce, ticket status, transfer/listing status, refund/cancel state.
6. Backend atomically records accepted/rejected result.
7. App shows accepted/rejected state with reason.

## Offline Fallback Concept

Offline scanner can:

- Validate signature and expiry if it has public verification material.
- Queue pending check-ins.
- Show `pending sync` state.

Risks:

- Duplicate redemption across multiple offline gates.
- Revoked/refunded ticket not known locally.
- Clock drift.

MVP should require online check-in unless a formal offline policy is implemented.

## Duplicate Redemption Prevention

- Database unique accepted check-in per ticket/event.
- Redis nonce lock for fast gate response.
- Idempotent check-in request ID.
- Staff UI shows already redeemed with last safe gate/time summary.

## Failure States

- Valid ticket.
- Already redeemed.
- Invalid ticket.
- Wrong event.
- Expired credential.
- Cancelled/refunded ticket.
- Listed ticket reserved for resale.
- NFC tag unreadable.
- NFC credential expired.
- Network unavailable.
- Unknown verification error.

## 2026-06-11 Fan iOS Dynamic QR Wiring

Status: native client wiring compiled; physical scan evidence still open

The fan-facing V4 Tickets entry-code sheet now calls the API-backed scanner service, which requests `/verification/qr` for the selected active ticket and encodes the returned signed payload as a QR image.

Client behavior:

- QR is generated from the backend payload only; the app does not synthesize signatures locally.
- Payload text, nonce, signature, and raw credential JSON are not displayed in UI.
- Expiry is decoded from `expiresAt`; the sheet refreshes again when 5 seconds or less remain.
- If QR refresh fails, the sheet shows a safe refresh/network message and does not present a stale credential as valid.
