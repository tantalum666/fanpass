## Purpose

The Web Beta Fallback is a backup delivery path while Apple Developer enrollment, TestFlight signing, and Apple Wallet signing are blocked. It should let the project demonstrate and validate the FanPass product concept through a browser without replacing the native iOS roadmap.

The fallback must support future dual-platform use: a fan should be able to use FanPass on web and iOS with the same account, same tickets, same resale listings, same proof history, and same organizer rules.

Web NFC is out of scope. Entry fallback is QR-only.

## Product Principle

Web and iOS are two clients for one FanPass account and one backend state model. Neither client should own business truth.

Single source of truth:

- User identity and roles: API plus Privy access-token sync.
- Events, venues, ticket types, and organizer rules: API/database.
- Ticket ownership, lifecycle, transferability, and proof history: API/database plus chain proof-sync where enabled.
- Checkout, refunds, and payment state: API plus Stripe test-mode webhooks.
- Resale listings, orders, trades, and market history: API/database.
- QR credential issuance, refresh, expiry, and redemption: API/database.
- Staff gate assignment and scanner authority: API/database.

## Recommended Architecture

Use a dedicated `apps/web` package when implementation starts.

Recommended stack:

- Vite React TypeScript.
- Clean V4 tokens from `docs/brand/fanpass-brand-tokens.json`.
- Shared API client layer under `apps/web/src/services`.
- Feature folders for `landing`, `auth`, `events`, `tickets`, `checkout`, `market`, `fan-access`, `scanner`, and `profile`.
- No Next.js unless a fresh dependency/security review proves a clean production path.
- No Web NFC package or browser NFC capability detection in the fallback.

Recommended root workspace change when coding begins:

- Add `apps/web` to root `workspaces`.
- Add root scripts such as `dev:web`, `build:web`, `typecheck:web`, and optionally `test:web`.
- Keep `apps/dashboard` as FanPass Console, not the fan web app.

## Dual-Platform Synchronization Model

### Identity

- Web and iOS must resolve to the same FanPass user through `privyId`, not email matching.
- A user can sign in on web and iOS and see the same wallet/tickets if the Privy account is the same.
- Role assignment remains server-side. Web clients must not request elevated roles.

### Ticket State

- Ticket status changes are server-owned.
- Web and iOS should render the same ticket statuses: `active`, `listed`, `sold`, `transferred`, `refunded`, `cancelled`, `expired`, and `redeemed`.
- Client-side optimistic updates are allowed only when reversible and must reconcile with the next API response.

### QR Credentials

- QR credentials are generated by the API.
- Web and iOS may display short-lived QR credentials, but neither should sign them locally.
- Refresh should supersede prior active credentials on the backend.
- Redemption must consume the accepted credential server-side.

### Resale And Market

- Listing creation, cancellation, buyer checkout, and transfer completion are API operations.
- Web and iOS should read the same market summary, orderbook, trades, cap, and listing state.
- Market copy should remain fan-readable and avoid trading-app language.

### Realtime

Initial fallback can use polling.

Later shared realtime path:

- Ticket wallet refresh after purchase/list/cancel/transfer.
- Market summary and trades refresh through WebSocket or polling.
- QR credential refresh timer.
- Scanner result polling only if a web scanner mode is built.

Exit criteria:

Exit criteria:

- Backend remains authoritative for redemption and duplicate rejection.
- Evidence is labeled web QR fallback only, not physical QR/NFC evidence.

Deliverables:

- Proof & History updates after lifecycle changes.
- Cross-client refresh guidance for iOS/web sync.

Exit criteria:

- A ticket listed on web appears listed on iOS after refresh, and vice versa once iOS staging read/write paths are enabled.

## Risks

| Risk | Mitigation |
| --- | --- |
| Web route is mistaken for native Beta readiness | Keep docs, evidence, commit messages, and UI copy labeled as Web Beta Fallback. |
| Web and iOS drift into separate products | Use shared API contracts, shared status names, shared Clean V4 tokens, and shared product copy. |
| Web app drifts into a marketing surface | Keep building the usable product app first: Discover, Event Detail, Market, Checkout, Tickets, Ticket Detail, resale, and proof states. |
| Route surfaces feel like separate products | Keep the route frame, navigation, typography scale, and compact operational rhythm consistent across all destinations. |
| Web checkout weakens payment boundary | Keep Stripe calls server-owned and test-mode only. |
| Web QR scanner is mistaken for physical scanner evidence | Add dedicated evidence naming and never mark native `ops-scanner` evidence closed from web proof. |
| Crypto language overwhelms mainstream positioning | Use `Verified Ticket`, `Secure Resale`, `Proof & History`, and `Transparent Prices`. |
